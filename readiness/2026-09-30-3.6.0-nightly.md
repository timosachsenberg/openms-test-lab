# Release readiness: OpenMS 3.6.0, nightly 2026-09-30 (checked 2026-09-30)

**Verdict: NOT READY**

This nightly has four wheels and four installers, all built from `55f7bdb`: develop after
OpenMS/OpenMS#10287, the last merge of 2026-09-29. It is the first nightly with:
- the third-party licenses (OpenMS/OpenMS#10292);
- the Linux and Windows wheels built on vcpkg (#10331, #10333);
- SQLite 3.53.1 in every wheel (#10342);
- no ProteoWizard, SpectraST or X!Tandem in the installers (#10292, #10344);
- the adapters' own engine lookup (#10304);
- the library permissions fix (#10324);
- the documentation that E5 to E7 asked for (#10322).

The checks show:
- **Fixed in this nightly:**
  - C4: CometAdapter and SageAdapter find the bundled engines without `-*_executable` (#10304);
  - E5, E6 and E7 (#10322);
  - the wheels' SQLite 3.49.2 (CVE-2025-6965): all four wheels carry 3.53.1 (#10342);
  - no group- or world-writable file in either DEB or the `.pkg` (#10324);
  - most of F8: every installer and wheel ships `THIRD-PARTY-NOTICES.txt` and the texts it lists (#10292).
- **Still blocking: F6**, now partly waived:
  - OpenSSL published CVE-2026-84782 (High, DTLS) on 2026-09-29. It affects 3.6.4, which **every artifact** carries: shared in both DEBs, the `.pkg` and the macOS wheel; static in the Linux and Windows wheels and in the Windows installer's `OpenMS.dll`.
  - The maintainer accepted this CVE for 3.6.0, and also the old zlib and expat in Comet and MaRaCluster ([waiver](https://github.com/timosachsenberg/openms-test-lab/pull/5#issuecomment-5905329695)).
  - **Not waived:** Sage 0.14.6 embeds SQLite 3.41.2 with FTS5, which three High CVEs affect by version. The copy was there on 2026-09-29 as well; this check is the first to see it.
- **Still blocking: F8**, down to four gaps:
  - `libgfortran` in both DEBs;
  - glib, harfbuzz and pcre2 in the `.pkg`;
  - the MSVC runtime DLLs of the Windows installer and wheel.
- **Newly blocking: E4.** zstd compression of mzML (#10287, merged at 20:01 UTC on 2026-09-29) is a headline feature that pyOpenMS exposes, and no user page describes it. OpenMS/OpenMS#10348 (open, CI green) adds the documentation.

## Blocking failures

1. **F6: bundled binaries contain library versions with High CVEs.**
   - **OpenSSL 3.6.4 in every artifact.**
     - On 2026-09-29, OpenSSL published 13 advisories that affect 3.6.4 (fixed in 3.6.5). One is High: CVE-2026-84782, "DTLS Retransmits Handshake Messages From a Stale Buffer Offset". The other twelve are Low.
     - Where it is:
       - shared: both DEBs, the `.pkg` and the macOS wheel;
       - static: in `libOpenMS` of the Linux wheels, and in `OpenMS.dll` of the Windows wheel and the Windows installer. The build paths show that the DTLS code is linked in.
     - The labs' `bundled-libs.py` now fails the DEBs and the `.pkg`, which turns B3, B6 and B7 red. It cannot see the static copies.
     - OpenMS opens no DTLS connections:
       - its own code calls no OpenSSL function;
       - in the installed x86_64 DEB, only `libcurl` and `libthrift` import TLS entry points (`TLS_method`, `TLS_client_method`, `SSL_connect`), and neither imports a DTLS method;
       - on Windows, curl uses Schannel.
     - `vcpkg.json` still pins `openssl` 3.6.4. vcpkg's registry had no 3.6.5 at 06:00 UTC.
     - **Waived for 3.6.0 by the maintainer** ([waiver](https://github.com/timosachsenberg/openms-test-lab/pull/5#issuecomment-5905329695)); the update follows via OpenMS/OpenMS#10270.
   - **Old copies in the bundled engines.** The engine binaries are unchanged since 2026-09-29.

     | Copy | Where | High or Critical by version |
     | --- | --- | --- |
     | zlib 1.2.3 in MaRaCluster 1.04.1 | x86_64 DEB, `.pkg`, Windows | CVE-2016-9841 and CVE-2016-9843 (9.8), CVE-2016-9840 (8.8), CVE-2018-25032 (7.5), and others that concern MiniZip, `untgz` or `inflateGetHeader` only |
     | zlib 1.2.11 in Comet 2025.01 rev. 1 | both DEBs, `.pkg`; the Windows `comet.exe` has zlib code but no version string | CVE-2018-25032 (7.5); CVE-2022-37434 (9.8, `inflateGetHeader` only) |
     | expat 2.2.9 in Comet (MSToolkit) | both DEBs, `.pkg`; the Windows `comet.exe` has expat code but no version string | 9 Critical, among them CVE-2022-25235 and CVE-2024-45492, and 18 High; fixed by 2.8.4 |
     | **SQLite 3.41.2 in Sage 0.14.6** (Rust `rusqlite`, built with FTS5) | all four installers | CVE-2025-6965 (7.7, fixed in 3.50.2); CVE-2026-11822 and CVE-2026-11824 (7.8, FTS5, fixed in 3.53.2) |

     - Comet and MaRaCluster: **waived for 3.6.0** in the same comment. They ship as they are, are listed under *Known issues* in the CHANGELOG (OpenMS/OpenMS#10348), and will be rebuilt after the release.
     - **Sage is not waived.** The copy was already in the 2026-09-29 artifacts, but that check did not look for it.
   - Gone since 2026-09-29: the wheels' SQLite 3.49.2 (#10342), SpectraST's zlib 1.2.5 (#10292) and X!Tandem's expat 2.0.1 (#10344).
2. **F8: four license gaps are left.**
   - #10292 works:
     - `THIRD-PARTY-NOTICES.txt` is in all eight artifacts, every number with one text and every text referenced;
     - `LICENSES/vcpkg/` has 145 to 150 port texts, without vcpkg's build helpers;
     - the vendored, Qt, Homebrew and system texts are where they belong;
     - every `THIRDPARTY/<tool>/` has its license, and the DEB installs `/usr/share/doc/openms/copyright`.
   - Still without a text:
     - both DEBs: `/usr/lib/libgfortran.so.5.0.0` (GPL-3.0 with the GCC Runtime Library Exception). The Linux wheels ship `LICENSES/system/libgfortran` for the same library;
     - `.pkg`: `libglib-2.0.0.dylib` and `libgthread-2.0.0.dylib` (glib, LGPL-2.1-or-later), `libharfbuzz.0.dylib` (MIT) and `libpcre2-8.0.dylib`/`libpcre2-16.0.dylib` (BSD).
       - The collector in `cmake/third_party_licenses.cmake` takes the formulae from `brew deps --installed --union qtbase qtsvg`. That list omitted glib, harfbuzz, pcre2 and cairo: the runner image had these preinstalled, and the build only upgraded them.
       - The macOS build logged "Packaging the license files of 29 Homebrew formulae".
     - Windows installer (9 DLLs) and wheel (3): the MSVC runtime. Microsoft's terms for these redistributables ask for no license text, so this gap may not count against the criterion ("each component that *requires* its license to accompany it").
3. **E4: zstd compression has no user documentation at `55f7bdb`.**
   - #10287 adds zstd compression of the mzML peak data, bound in pyOpenMS as `PeakFileOptions.setZstdCompression`. It is a bullet of *OpenMS Library* in the CHANGELOG.
   - Only the FileConverter and FileFilter tool pages list the new options. `file-formats.md` and the pyOpenMS `mzml_files.rst` do not mention zstd.
   - OpenMS/OpenMS#10348 adds a section to both. Its code runs against this nightly's wheel, and its CI is green.

## Other findings

- **The labs' F6 cannot see static copies, and there are more of them now.** Since #10331 and #10333, the Linux and Windows wheels link OpenSSL, curl, SQLite and zlib statically, and so does the Windows installer's `OpenMS.dll`. `bundled-libs.py` finds nothing in them. The by-hand scan read their version strings. The 2026-09-29 report suggested teaching the script to scan every binary; that is now the only way the labs can judge the wheels.
- **The notices of the Windows installer and wheel are not valid UTF-8.** `LICENSES/vcpkg/openms-thermo-bridge.txt` is vcpkg's concatenation of the Thermo `.doc` and the bridge's BSD text; on Windows the `.doc` part is cut to 6 bytes. The BSD text is complete. The Apache-2.0 text appears twice in the installers' notices, from vcpkg and from ThermoRawFileParser (line ends differ).
- **A tag does not upload the wheels to PyPI.** `pyopenms-wheels-cibuildwheel.yml` builds on `v*` tags, but its `Upload release to PyPI` job runs only on a `workflow_dispatch` of a `v*` tag with `upload-to-pypi` set. G6 therefore needs that dispatch after the tag.
- **The pyOpenMS API reference is still built from pyOpenMS 3.5.0** in Documentation Validation (see 2026-09-29).
- Unchanged:
  - `FileInfo` rejects `.raw` input (exit 6);
  - `SageAdapter` leaves its configuration JSON and `results.sage.*` behind.
- Reproduce any of this with the commands in [RELEASE-READINESS.md](../RELEASE-READINESS.md).
