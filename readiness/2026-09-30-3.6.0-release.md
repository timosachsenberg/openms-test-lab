# Release readiness: OpenMS 3.6.0, release v3.6.0 (checked 2026-09-30, rechecked 2026-10-01)

**Verdict: NOT READY**

The maintainer tagged `v3.6.0` at 08:24 UTC on `5d5cbff405`. That commit is the 2026-09-30 nightly's `55f7bdb` plus OpenMS/OpenMS#10348, which documents zstd compression, adds *Known issues* to the CHANGELOG and dates its heading. The workflows the tag started published:
- the installers and the source tarball as [Release 3.6.0](https://github.com/OpenMS/OpenMS/releases/tag/v3.6.0) (marked latest) and on archive.openms.de;
- the wheels on archive.openms.de;
- the documentation and the container images.

This report checks these published files.

**The packages pass.**
- Every check of A–F that concerns the artifacts passes, except the parts of F6 and F8 that the maintainer waived for 3.6.0.
- All nine labs install and run the release files. C1–C3 pass on every platform, with the same test counts as the nightly.
- The version is a clean `3.6.0` everywhere (G2). E4 passes since #10348.
- Apart from version strings, revision, build times and signatures, every binary is byte-identical to the 2026-09-30 nightly's. The one exception: the Windows wheel was compiled with a slightly older MSVC.

**The release is not finished.** None of the following needs a new build, but each needs a maintainer:
- the pyOpenMS documentation of 3.6.0 is not online (E10);
- the GitHub release notes are cut off and their download link is dead; several installation pages and the README point to 3.5.0 (G8);
- the Windows installer is unsigned (G10);
- Bioconda (G7) does not have 3.6.0 yet.

**Added at 13:10 UTC:** PyPI has served pyOpenMS 3.6.0 since 12:03 UTC, and G6 passes (see G6 below).

## Blocking failures

Each needs a maintainer; none needs a rebuild. The order is the order that helps users most.
1. **G10: the Windows installer is not signed.**
   - `osslsigncode verify` finds no signature in either copy.
   - `openms.de/download/` already redirects to the GitHub release, and archive.openms.de's `release/latest/` serves the same file, so this unsigned `.exe` is what users get now.
   - Fix: sign it and replace both copies. The website PR OpenMS/OpenMS-website#289 is still unmerged; it was checked at 10:46 UTC.
2. **G8: the release notes and several links are wrong.**
   - **The release notes are cut off.** The GitHub release body is the template plus the 3.6.0 CHANGELOG section (126,967 characters). GitHub keeps 124,999 characters of it, so the notes stop mid-word in *Build System* ("…in-process Therm"). Lost with it are the *Known issues*, where the CHANGELOG discloses the waived vulnerabilities, and the sign-off.
   - **The only download link is dead.** "Grab it here" points to `abibuilder.cs.uni-tuebingen.de/archive/openms/OpenMSInstaller/release/3.6.0`, which returns 404: abibuilder has received no uploads since June, and its newest nightly is from 2026-06-11. The link comes from `.github/workflows/release-announcement.txt`, and the website PR #289 contains it too.
   - **Pages that serve 3.5.0.** The macOS and Windows installation pages and `README.md` link to abibuilder's `release/latest/`, which serves 3.5.0 installers and documentation. The Linux page uses GitHub's `releases/latest` and is right. archive.openms.de's `release/latest/` has 3.6.0.
   - **A dead container tag.** The installation pages tell users `docker pull ghcr.io/openms/openms-library:3.6.0`, rendered on openms.readthedocs.io `stable`. That tag does not exist: `containerdeploy.yml` strips a `Release` prefix but not a `v`, so the images are tagged `v3.6.0`. 3.5.0's were `3.5.0`.
   - Fix:
     - replace the release body with a shortened one;
     - correct the link in #289 before merging;
     - add the tag `3.6.0` to the four images (`docker buildx imagetools create --tag …:3.6.0 …:v3.6.0`);
     - point the pages to archive.openms.de, or redirect abibuilder there. Pages fixed in `develop` reach `latest` at once, but `stable` only with the next tag.
3. **E10: pyOpenMS has no online documentation for 3.6.0.**
   - All 154 `Full documentation:` URLs of the tools answer 200 (`openms.de/doxygen/release/3.6.0/html/TOPP_*.html`).
   - `pyopenms.readthedocs.io/en/<version>/` returns 404 as `3.6.0`, `v3.6.0`, `release-3.6.0` and `stable`.
   - The Read the Docs project `pyopenms` has no version for the tag. Its default version is still `release-3.5.0`, and its last build ran on 2026-04-30: `latest` shows "pyOpenMS 3.5.0dev documentation".
   - The `openms` project, in contrast, built `stable` from the tag at 08:25 UTC. That points to a broken connection between GitHub and the `pyopenms` project; this is an inference, not verified.
   - Fix: resync the versions or reconnect the project, build `v3.6.0` and make it the default.
4. **Not run yet: G7.** A blocking check that has not run caps the verdict. The Bioconda recipes are still at 3.5.0. Their update has to follow the new tag URL and the new tarball layout (G3).

## Other findings

- **The 3.6.0 DEBs do not install on Ubuntu 26.04 or Debian 13** ([OpenMS/OpenMS#10351](https://github.com/OpenMS/OpenMS/issues/10351), reported by a user on 2026-09-30; added on 2026-10-01).
  - Both published DEBs (amd64 and arm64) depend on the Qt packages under the names they have on Ubuntu 24.04, the build host: `libqt6core6t64`, `libqt6gui6t64`, `libqt6opengl6t64`, `libqt6openglwidgets6t64` and `libqt6widgets6t64`. This was read from their control files.
  - Ubuntu 26.04 names the last four without the `t64` suffix, so apt cannot install the DEB there (#10351). Debian 13 does the same, according to the tests in OpenMS/OpenMS#10367; this report did not repeat them.
  - The installation page says that the DEB "is tested on Ubuntu 24.04 and needs glibc 2.38 or newer". That reads as if newer releases work.
  - C6 passed, because the glibc floor matches the docs, and the labs install the DEB only on Ubuntu 24.04. A lab job that installs the DEB on Debian 13 or Ubuntu 26.04 would have caught this.
  - `develop` fixes it for the next release:
    - OpenMS/OpenMS#10352 added the old names for core, gui and widgets; the 2026.10.01 nightly still depends strictly on the opengl and openglwidgets packages;
    - OpenMS/OpenMS#10367, merged on 2026-10-01 at 08:34 UTC, adds them for all five. Its author installed the resulting package on Ubuntu 26.04 and Debian 13.
  - For 3.6.0 itself there are two options:
    - #10367's script could rewrite the control member of both DEBs; the data member stays byte-identical. Their GitHub assets could be replaced at the same time as the signed `.exe`;
    - otherwise the release notes should list the problem under *Known issues*. The proposed release notes now do.
- **What the release workflow should do differently next time.** These are the causes of blocking failure 2. `develop` has fixed all three since 2026-09-30 (OpenMS/OpenMS#10354 and OpenMS/OpenMS#10355):
  - `release-announcement.txt` links to abibuilder;
  - `release.yml` puts the whole CHANGELOG section into the release body, which has a limit of 125,000 characters;
  - `containerdeploy.yml` keeps the `v` of a tag in the image tag.
- **The PyPI upload rebuilds instead of publishing what was tested.**
  - `pyopenms-wheels-cibuildwheel.yml` uploads to PyPI only from a `workflow_dispatch`, and that dispatch builds all wheels again.
  - So the published wheels are not byte-identical to the ones checked here; G6 tested them again. The dispatch also overwrote the tested wheels on archive.openms.de.
  - The builds can differ: the tag's Windows wheel was compiled with MSVC 19.51.36257.0 on runner image 20260922.246.2, while the nightly's used 19.51.36260.0 on 20260925.250.1.
  - Publishing the tag run's artifacts would avoid all of this.
- **The nightly Doxygen documentation that nightly tools link to is stale.**
  - Nightlies deploy to `Documentation/nightly/<date>/` and `nightly/latest/`.
  - `Documentation/nightly/html/`, which `openms.de/doxygen/nightly/html/…` serves, was last written on 2026-07-29; its FileConverter page has no zstd option.
- **abibuilder is frozen, and it is the only copy of some files:**
  - older installers (archive.openms.de's `OpenMSInstaller/release/` has only `3.6.0/` and `latest/`);
  - the tutorial data, which the TOPPView tutorial and the pyOpenMS user guide link to (`archive.openms.de/openms/Tutorials/` is 404).
