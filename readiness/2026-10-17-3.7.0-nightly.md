# Release readiness: OpenMS 3.7.0, nightly 2026-10-17 (checked 2026-10-17)

**Verdict: NOT READY**

The nightly of 2026-10-17 is complete: four wheels and four installers, all built from
`1868c06d04`. That revision is develop after OpenMS/OpenMS#10600, the fix for the pyOpenMS API
reference (OpenMS/OpenMS#10599). The whole release matrix ran on it with the lab's new checks:
- C3 for ONNX and Thermo builds;
- C5 through a symbolic link;
- C6 on every documented distribution;
- C9 (OpenMP);
- C10 for the x64 container image;
- E11, the documentation as rendered.

Linux x64, Linux arm64 and macOS pass everything the labs check. One blocking check fails:
- **C3 on Windows:** `TOPP_OpenDIA_auto_transition_list_sqlite` fails because a TempDir name
  pushes OpenDIA's SQLite journal past `MAX_PATH`. The fix, OpenMS/OpenMS#10614, was merged into develop as `bfdbe626a2` at 19:21 UTC,
  after this nightly was built; the next nightly has to show C3 green on Windows.

Other blocking checks did not run and cap the verdict:
- C10 for the arm64 image, because the Container lab is not on the lab's default branch;
- E9 (Documentation Validation), which has no run on this revision;
- F7 and F8 (signatures, licenses);
- the judgement checks D5 and E4.

E8 fails, which blocks at release: the CHANGELOG has an orphaned line.

## Blocking failures

1. **C3 on Windows: `TOPP_OpenDIA_auto_transition_list_sqlite` fails** (B1). The other 2329
   selected tests pass, and 99 are skipped as not registered for this package.
   - The test stops with SQLite's "unable to open database file" while it prepares the
     peptide query.
   - Cause: OpenDIA keeps its intermediates in a run-owned `TempDir`, named
     `OpenMSTempDir_<date>_<time>_<hostname>_<pid>_<n>_<full UUID>` (about 90 characters).
     From the test directory under `%TEMP%`, the scratch PQP or its `-journal` crosses
     `MAX_PATH` (259). The executables are not long-path aware, so `LongPathsEnabled=1` does
     not help. Measured on windows-2025: up to 207 characters of intermediate path work, 213
     fail on the journal.
   - Fix: OpenMS commit
     [`eaddbdd5`](https://github.com/OpenMS/OpenMS/commit/eaddbdd5bb44de3ecf74c928596f56dd8c3ea26a)
     on branch `claude/openms-test-release-readiness-ks3twg` (shorter TempDir names, and a
     test). CI is green on it ([Build and Test 38414258466](https://github.com/OpenMS/OpenMS/actions/runs/38414258466)).
     The PR is [OpenMS/OpenMS#10614](https://github.com/OpenMS/OpenMS/pull/10614), merged on
     2026-10-17 at 19:21 UTC as `bfdbe626a2` (not in this nightly).

E8 (blocking at release) is listed under the checks and has to be fixed before the release-prep
commit.

## Other findings

- **F6, by hand: old zlib and SQLite inside bundled engines.** These do not block F6 as defined:
  OpenSSL is clean, and none of these copies is known to be reachable.
  - The DEBs' THIRDPARTY engines carry static zlib 1.2.11 (Comet) and zlib 1.2.3 (MaRaCluster).
    Both predate the fixes for CVE-2018-25032 (High, deflate with many distant matches) and
    CVE-2022-37434 (Critical, only through `inflateGetHeader`).
  - Sage carries static SQLite 3.41.2 (on Windows as well), before the fix for CVE-2023-7104
    (session extension).
  - The Windows installer ships Qt 6.8.3, macOS ships Qt 6.12.0; Qt's advisories for 6.8.3 were
    not reviewed.
  - A person should confirm that the engines never use `inflateGetHeader` or the SQLite session
    extension, or the engines should be updated.
- **F6: the macOS pkg ships two OpenSSL major versions.** It ships `libcrypto.4.dylib` (OpenSSL
  4.0.3, from Homebrew `openssl@4`) beside the OpenSSL 3.6.5 of the rest of the package. Neither
  has a known advisory.
- **E11 found the 3.6.0 API reference broken in the same way as OpenMS/OpenMS#10599.** The
  published `v3.6.0` docs on Read the Docs still show it. It cannot change without a new wheel,
  because the pages are generated from the release wheel's docstrings: 3.6.1 or 3.7.0.
