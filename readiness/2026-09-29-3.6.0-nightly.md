# Release readiness: OpenMS 3.6.0, nightly 2026-09-29 (checked 2026-09-29)

**Verdict: NOT READY**

This nightly has four wheels and four installers, all built from `088f8ac`: develop after
OpenMS/OpenMS#10314, the last merge of 2026-09-28. It is the first nightly with the user
documentation of the headline features, FileHandler's Thermo peak picking (OpenMS/OpenMS#10303),
the readiness cleanups (OpenMS/OpenMS#10305) and the Debian package fixes (OpenMS/OpenMS#10259).
The checks show:
- **Fixed in this nightly:**
  - E4: every headline feature has a user page or section (OpenMS/OpenMS#10293, #10296, #10297,
    #10298, #10302);
  - A3: the version is `3.6.0` everywhere, including both Sphinx `conf.py` files (#10293);
  - C7: a nightly DEB now sorts below its release, and 3.5.0 upgrades to it without leftovers
    (#10305);
  - D4, F3 and F4 (#10305).
- **Still blocking: F8**, third-party licenses. OpenMS/OpenMS#10292 is open; its CI is green
  apart from the Windows wheel, which was still building when this report was written.
- **Newly blocking: F6.** This check looked at static copies inside the binaries for the first
  time, not only at the libraries the lab script finds by file name:
  - all four wheels link SQLite 3.49.2 into libOpenMS (CVE-2025-6965, NVD 7.7 HIGH, fixed in
    3.50.2);
  - the MaRaCluster of the DEB and the `.pkg` embeds zlib 1.2.3, and their Comet zlib 1.2.11
    (CVE-2018-25032, NVD 7.5 HIGH, fixed in 1.2.12; 1.2.3 has older High and Critical ones
    too).
  - Apart from the MaRaCluster that the `.pkg` bundles now, the 2026-09-28 nightly had the same
    copies. The labs' automated F6 passes because `bundled-libs.py` cannot see them.
- **New finding outside the checks:** both DEBs install 54 libraries world-writable (mode 0777)
  into `/usr/lib`, `libssl.so.3` and `libcrypto.so.3` among them. OpenMS/OpenMS#10324 (open)
  fixes it.

## Blocking failures

1. **F6: bundled binaries contain library copies with High CVEs.**
   - **Wheels:** all four link SQLite 3.49.2 (source id `2025-05-07 10:39:52 17144570b0`)
     statically into `libOpenMS` / `OpenMS.dll`. CVE-2025-6965 (an integer overflow in the core
     engine when an attacker can inject SQL; fixed in 3.50.2) is rated NVD CVSS 3.1 7.7 HIGH.
     The copy is the amalgamation that OpenMS vendors with SQLiteCpp
     (`src/openms/extern/SQLiteCpp/sqlite3`, compiled in with `SQLITECPP_INTERNAL_SQLITE`),
     which the wheels use because they build without `USE_EXTERNAL_SQLITECPP`. The installers
     use vcpkg's SQLiteCpp and SQLite 3.53.1 instead. The vcpkg-built Linux and Windows wheels
     that OpenMS/OpenMS#10331 and #10333 introduce keep the vendored copy.
   - **Installers:** the THIRDPARTY tools link old zlib statically:

     | Binary | zlib | Applicable NVD entries |
     | --- | --- | --- |
     | MaRaCluster 1.04.1 (x86_64 DEB, `.pkg`) | 1.2.3 | CVE-2016-9841 and CVE-2016-9843 (9.8 CRITICAL), CVE-2016-9840 and CVE-2016-9842 (8.8 HIGH), all fixed in 1.2.9; CVE-2018-25032 (7.5 HIGH) |
     | Comet (x86_64 DEB, `.pkg`) | 1.2.11 | CVE-2018-25032 (7.5 HIGH, deflate, fixed in 1.2.12) |
     | SpectraST (x86_64 DEB) | 1.2.5, inflate only | CVE-2016-9840 to 9842 |

     - The versions come from zlib's "deflate/inflate 1.2.x Copyright" strings. Percolator
       and the other engines have none; the `.pkg`'s `percolator` links only `libc++` and
       `libSystem`. The Windows installer's engines were not scanned.
     - CVE-2022-37434 (9.8 CRITICAL, up to 1.2.12) applies too, but only to programs that call
       `inflateGetHeader`. Whether these do was not analysed, and neither was whether the other
       code paths are reachable.
   - The 2026-09-28 artifacts had the same copies, except that the `.pkg` had no MaRaCluster;
     the DEB's older MaRaCluster 0.05.0 embedded zlib 1.2.3 as well. `bundled-libs.py` finds
     libraries by file name, so every lab passes F6.
   - Fixes, for a maintainer to decide: the vendored SQLite amalgamation updated to 3.50.2 or
     newer, or the wheels built with `USE_EXTERNAL_SQLITECPP=ON` against vcpkg's SQLite;
     THIRDPARTY builds of MaRaCluster and Comet against a current zlib; OpenMS/OpenMS#10292
     already removes SpectraST.
2. **F8: third-party licenses do not ship with what they cover.**
   - `share/OpenMS/LICENSES/` holds the OpenMS license and, new from #10259, Thermo's
     `ThermoRawFileReader-License.doc`, in the DEBs, the `.pkg` and the wheels.
   - Still without a text: the 53 vendored libraries of the DEB; the `.pkg`'s 67 third-party
     dylibs and 8 Qt frameworks; the libraries of each wheel (115 dylibs in the macOS wheel);
     Comet, MaRaCluster, Percolator, SpectraST and X!Tandem; the Thermo bridge's `CommandLine.dll`
     and `OpenMcdf*.dll`; ThermoRawFileParser's 33 .NET assemblies; the static SQLite of the
     wheels.
   - OpenMS/OpenMS#10292 (open) covers all of these except the MSVC runtime DLLs of the Windows
     wheel, which its description lists as not covered.

## Other findings

- **Both DEBs install 54 files world-writable** (mode 0777, `root:root`, directly in
  `/usr/lib`): the 53 vendored libraries, `libssl.so.3` and `libcrypto.so.3` among them, and
  `libopenms_thermo_bridge.so`.
  - Any local user can replace code that the OpenMS tools load, also when root runs them.
  - The 2026-09-28 x86_64 DEB was the same. The `.pkg` has 4,368 world-writable files: the
    2,184 headers and resources of its Qt frameworks (0777) and their AppleDouble companions
    (0666).
  - The cause is `GROUP_WRITE WORLD_WRITE` in the `install(RUNTIME_DEPENDENCY_SET …)` of
    `cmake/package_general.cmake`. OpenMS/OpenMS#10324 drops them, and its CI is green apart from
    the Windows wheel, which was still building.
- **The lab's F6 cannot see static copies.** `bundled-libs.py` identifies libraries by file name,
  so SQLite in libOpenMS and zlib in the THIRDPARTY executables passed every lab. The by-hand
  check found them from their version strings (`sqlite_source_id`, "deflate 1.2.x Copyright").
  Teaching the script to scan every binary for these strings would make F6 catch them in the
  labs.
- **Attempt 1 of the wheel run failed on infrastructure.** The Windows build could not download
  the Thermo test file: curl's schannel reported `CRYPT_E_REVOCATION_OFFLINE` for the certificate
  revocation check. The re-run passed. `--ssl-revoke-best-effort` in
  `tools/ci/fetch_thermo_assets.sh` would make the download tolerate an unreachable revocation
  server.
- **The pyOpenMS API reference is built from pyOpenMS 3.5.0.** `doc/pyopenms/docs/install_pyopenms.py`
  installs the latest release from PyPI outside ReadTheDocs, so the Documentation Validation run
  checks the 3.6 user guide against the 3.5.0 API. Its 447 warnings, mostly docutils errors in
  docstrings, therefore say little about 3.6.
- **Installing over an older nightly needs `--allow-downgrades` once.** The nightlies before
  #10305 declare plain `3.6.0`, which sorts above `3.6.0~nightly.2026.09.28`, so
  `apt-get install -y` refuses this nightly over them ("Packages were downgraded and -y was used
  without --allow-downgrades"). A machine that keeps such a nightly will also see the 3.6.0 release
  as the version it already has.
- **The 3.5.0 DEB cannot be installed next to `libsqlite3-dev`**: it ships `/usr/include/sqlite3.h`.
  The 3.6 nightlies do not. Found while preparing C7.
- **FileInfo cannot inspect Thermo `.raw` or Bruker `.d` input.** `FileInfo -in <file>.raw` exits
  6 ("invalid format 'raw'"), although FileHandler reads both and 24 installed tools accept
  `raw`. The C5 cross-check used DIAuditor and pyOpenMS `FileHandler` instead.
